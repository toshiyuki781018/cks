# 問題04：不審なコンテナの実行を検知し封じ込める

## 対象領域

Runtime Security / System Hardening

## 教材種別

Drill（試験対策問題）

目安時間：15〜20分

# 背景

Kubernetesクラスター上で稼働しているアプリケーションについて、セキュリティ監視から不審な動作が報告されました。  

調査の結果、`ollama`に関連するいずれかのPodが、Node上のシステムメモリへ  
直接アクセスできる機密性の高いデバイスファイルを読み取っている可能性があります。

しかし、現時点ではどのPodがアクセスしているのか特定できていません。  
クラスターにはRuntime Securityの監視ツールとしてFalcoがインストールされています。

不審なアクセスを検知するためのルールを作成し、実際のRuntimeイベントからアクセス元のコンテナを特定してください。  
その後、コンテナを実行しているPodとDeploymentを特定し、不審なWorkloadを停止してください。

# 初期観測情報

セキュリティ監視から、次の情報が得られています。

```text
対象アプリケーション群：ollama
不審なアクセス先：/dev/mem
```

`/dev/mem`は、システムの物理メモリへアクセスするためのデバイスファイルです。

複数のDeploymentが稼働しているため、Deployment名だけから停止対象を判断することはできません。  
また、クラスターにはFalcoがインストールされており、ローカルルールを定義できる状態になっています。

# 要件

以下の要件をすべて満たしてください。

1. `/dev/mem`へのアクセスを検知できるFalcoルールを作成すること。
2. 検知イベントから、アクセスを行ったコンテナを識別できる情報を取得すること。
3. 検知結果を根拠として、不審なコンテナを実行しているPodを特定すること。
4. 特定したPodを管理しているDeploymentを特定すること。
5. 不審なDeploymentのReplica数を`0`にして、Workloadを停止すること。
6. 不審なDeployment以外のWorkloadへ影響を与えないこと。

# 設定情報

| 項目           | 設定内容                                |
| ------------ | ----------------------------------- |
| 監視ツール        | Falco                               |
| Falcoローカルルール | `/etc/falco/falco_rules.local.yaml` |
| 検知対象         | `/dev/mem`                          |
| 対象アプリケーション群  | `ollama`                            |
| 検知時のPriority | `NOTICE`                            |
| 停止方法         | 対象DeploymentのReplica数を`0`にする        |

# 制約

* 停止対象をDeployment名だけから推測してはいけません。
* Falcoによる検知結果を根拠として停止対象を特定してください。
* 不審なDeployment以外のDeploymentを変更してはいけません。
* Deploymentを削除してはいけません。
* Podを直接削除することで対応してはいけません。
* 不審なDeploymentについては、Replica数を`0`へ変更する操作のみ許可します。
* 既存のFalco標準ルールファイルを直接変更してはいけません。
* 検知ルールはローカルルールファイルへ作成してください。

# 完了条件

以下をすべて満たした場合、作業完了とします。

* `/dev/mem`へのアクセスをFalcoで検知できる。
* Falcoの検知結果からアクセス元コンテナを識別できる。
* 検知したコンテナからPodを特定できている。
* Podから管理元Deploymentを特定できている。
* 特定したDeploymentのReplica数が`0`になっている。
* 不審なPodが停止している。
* 他のDeploymentが変更されていない。

# 作業後の確認項目

対応後、次の内容を確認してください。

* 作成したFalcoルールが読み込めること。
* `/dev/mem`へのアクセスイベントを検知できること。
* 検知ログにアクセス元を追跡するための情報が含まれていること。
* 検知したコンテナとPodの対応関係を確認できること。
* 対象Podを管理しているDeploymentを確認できること。
* 対象DeploymentのReplica数が`0`になっていること。
* 対象Podが停止していること。
* 他のDeploymentが正常に稼働していること。

# 注意事項

今回の目的は、**「怪しそうなDeploymentを探して停止すること」** ではありません。  
Runtimeで実際に発生しているイベントを観測し、その証拠から停止対象を特定してください。

```text
不審な動作が報告される
        ↓
何を観測すればよいか考える
        ↓
/dev/memへのアクセス
        ↓
Falcoで検知
        ↓
実行主体を識別できる情報を取得
        ↓
コンテナを特定
        ↓
Podを特定
        ↓
Deploymentを特定
        ↓
対象だけを停止
```

また、検知ルールでは単に、

```text
/dev/memへアクセスした
```

という事実だけを出力するのではなく、  
**「そのイベントを発生させた実行主体を、その後の調査で追跡できるか」**  
を考えて出力内容を設計してください。

セキュリティインシデントへの対応では、

```text
検知
 ↓
証拠
 ↓
特定
 ↓
封じ込め
```

を根拠なく飛ばさないことが重要です。

今回も、Falcoで取得したRuntimeの観測結果を根拠として、影響範囲を限定した対応を行ってください。
