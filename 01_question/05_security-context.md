# 問題05：コンテナの実行時変更と権限を制限する

## 対象領域

System Hardening / Minimize Microservice Vulnerabilities

## 教材種別

Drill（試験対策問題）

目安時間：10〜15分

# 背景

`sec-ns` Namespaceでは、社内アプリケーションを`secdep` Deploymentとして運用しています。  

セキュリティレビューの結果、現在のコンテナは実行時にRoot Filesystemを書き換えることができ、  
プロセスの実行権限についても十分な制限が設定されていないことが確認されました。

コンテナが侵害された場合の影響を抑えるとともに、実行中のコンテナイメージ由来のFilesystemが  
変更されない状態を維持するため、既存Deploymentのセキュリティ設定を強化してください。

対象Deploymentのマニフェストファイルは事前に用意されています。

# 初期観測情報

対象となるDeploymentは次の通りです。

```text
Namespace  : sec-ns
Deployment : secdep
```

Deploymentには2つのコンテナが含まれています。

```text
sec-ctx-demo-1
sec-ctx-demo-2
```

それぞれのコンテナには、アプリケーションがデータを書き込むためのVolumeがマウントされています。

```text
sec-ctx-demo-1
    ↓
/data/demo1

sec-ctx-demo-2
    ↓
/data/demo2
```

現在のコンテナ実行設定では、セキュリティレビューで要求されている実行ユーザー、Filesystem、権限制御が設定されていません。

# 要件

以下のセキュリティ要件を、Deployment内の**すべてのコンテナ**で満たしてください。

1. コンテナ内のプロセスをUID `3000`で実行すること。
2. コンテナイメージ由来のRoot Filesystemを実行中に変更できないようにすること。
3. コンテナ内のプロセスが、実行開始後に現在より高い権限を取得できないようにすること。
4. アプリケーションがデータ保存用として使用する既存Volumeは引き続き利用できること。
5. Deploymentの既存Workload構成を維持すること。

# 設定情報

| 項目                | 設定内容                       |
| ----------------- | -------------------------- |
| Namespace         | `sec-ns`                   |
| Deployment        | `secdep`                   |
| マニフェスト            | `~/sec-ns_deployment.yaml` |
| Container 1       | `sec-ctx-demo-1`           |
| Container 2       | `sec-ctx-demo-2`           |
| 実行UID             | `3000`                     |
| Container 1の書き込み先 | `/data/demo1`              |
| Container 2の書き込み先 | `/data/demo2`              |

# 制約

* 対象Deploymentを削除・再作成してはいけません。
* コンテナイメージを変更してはいけません。
* コンテナのcommandを変更してはいけません。
* 既存Volumeを削除してはいけません。
* 既存のVolume Mountを削除・変更してはいけません。
* セキュリティ要件を満たすために必要な範囲のみマニフェストを変更してください。
* 2つのコンテナの両方が同じセキュリティ要件を満たすようにしてください。

# 完了条件

以下をすべて満たした場合、作業完了とします。

* `sec-ctx-demo-1`がUID `3000`で実行される設定になっている。
* `sec-ctx-demo-2`がUID `3000`で実行される設定になっている。
* 両方のコンテナでRoot Filesystemへの書き込みが禁止されている。
* 両方のコンテナで実行中の権限昇格が禁止されている。
* `/data/demo1`および`/data/demo2`の既存Volume Mountが維持されている。
* Deploymentの既存構成が維持されている。

# 作業後の確認項目

設定後、次の内容を確認してください。

* 2つのコンテナそれぞれに必要なセキュリティ設定が行われていること。
* 両方のコンテナがUID `3000`で実行されること。
* コンテナイメージ由来のRoot Filesystemが読み取り専用になっていること。
* プロセスが実行中に権限を昇格できないこと。
* 既存Volumeが削除されていないこと。
* `/data/demo1`および`/data/demo2`が引き続き利用できる構成になっていること。

# 注意事項

今回の目的は、単にコンテナを非rootユーザーで実行することだけではありません。  
コンテナが実行された後に、

```text
コンテナ内のプロセス
        ↓
Root Filesystemを書き換える
        ↓
起動時とは異なる状態になる
```

ことを制限する必要があります。

一方で、**「コンテナを変更できないようにする」＝「すべての書き込みを禁止する」**ではありません。  
今回のDeploymentには、アプリケーションがデータを書き込むためのVolumeがすでに用意されています。

```text
コンテナイメージ由来のFilesystem
        ↓
変更させない

書き込みが必要なデータ
        ↓
Volume
        ↓
/data/demo1
/data/demo2
```

という役割の違いを意識してください。

また、実行ユーザーを制限するだけでは、  
プロセスが実行中により高い権限を取得する可能性まで制御できるとは限りません。

```text
誰として実行するのか
        +
実行中に権限を上げられるのか
        +
どこを書き換えられるのか
```

という複数の観点から、コンテナ単位で必要な設定を判断してください。
